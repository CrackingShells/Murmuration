## (a) the message, from what colgrep reports

Finding before the fix: `colgrep init -y` exits 0 in both cases and writes its report on stderr, not stdout. Fresh folder: `Indexed <folder> (added: 1, changed: 0, deleted: 0, unchanged: 0)`. Lab under an indexed parent: `Indexed <parent> (subdir: lab2) (added: 1, ...)` or, with nothing to do, `Index is up to date for <parent> (4 files)`. The old script prints "built the colgrep index" whenever the exit status is 0 (read from the code, not re-run), which holds in both [source: raw output in `/private/tmp/murmuration-w04/author-w04-6/`, commands in the transcript; S-w03-reproducer-w03-2-7].

What would differ if the fix were wrong: the lab-in-parent line would still start with "built", or the fresh-folder line would not. The selftest asserts both.

Fix: `describe_index(report, root)` reads the last `Indexed ...` / `Index is up to date for ...` line of colgrep's stderr+stdout and compares the folder colgrep names with the lab folder (by realpath):
- same folder, `Indexed`: "built the colgrep index of the lab (added: ...), without the paths in .ignore"
- same folder, `up to date`: "the colgrep index of the lab was already there and up to date (N files)"
- another folder: "no new colgrep index: the lab is inside the index of <folder>, which colgrep updated|found up to date (...); searches from the lab use it"
- output of any other shape: "ran `colgrep init`; it said: <its last 200 characters>".

Selftest output (two real colgrep runs, scratch store, `TMPDIR` under the scratch folder):

### independent result
Selftest rerun (colgrep 1.6.2, scratch `/private/tmp/murmuration-w04/reproducer-w04-6/`, `COLGREP_DATA_DIR` and `TMPDIR` inside it): `PASS lab_init`, 4.3 s; both SELFTEST lines match the claim's (fresh: "built ... (added: 1 ...)"; lab in parent: "no new colgrep index: the lab is inside the index of <parent>, which colgrep updated (...)"). The full command is the quick one, so nothing more to run.

Own checks, with real colgrep (raw files `e1.err`, `e2.err`, `e5.err`, `e6.err` in the scratch folder) and fake `colgrep` scripts on PATH (`fake/colgrep`):
- Stream and exit: `colgrep init -y` exits 0 and prints nothing on stdout in every case; the report is on stderr. As claimed.
- Fresh lab end to end (`lab_init.py --project`): "built the colgrep index of the lab (added: 4 ...)". Lab inside an indexed parent: "no new colgrep index: the lab is inside the index of <parent>, which colgrep updated (added: 4, ... unchanged: 1); searches from the lab use it". Lab `.ignore` is respected inside the parent's index (a file under `__statera__/handbacks/` and one under `raw/` were not found by `colgrep search`; a plain note was). So "searches from the lab use it" holds.
- Parent up to date, lab unchanged: "found up to date (2 files)" parsed correctly; `(subdir: lab)` form parsed; paths with parentheses parsed; CRLF parsed.
- colgrep absent (PATH without it): the line says so, the lab is made, exit 0. Exit 1: "index not built (exit 1)". Hang (timeout 1 s): "index not built (TimeoutExpired)". Output of an unknown shape: passed through with colgrep's words. Second `/lab` call (question add): no index line, as before.
- Old behaviour: `git show 9e4bbac` confirms old `build_index` returned "built the colgrep index" on any exit 0.

Findings that do not match the claim or its main risk:
1. Lab with nothing to index. Real colgrep on an empty folder prints `Index is up to date for <folder> (0 files)` (exit 0, nothing built), and `describe_index` turns it into "the colgrep index of the lab was already there and up to date (0 files)". That is false: there was no index. A real `/lab` writes framing, wave note and user_words before the build, so it has files and does not reach this case; the claim scope does not list it and the selftest does not cover it.
2. "Never fails a `/lab` because of the message" does not hold for one input. A `colgrep` whose output is not valid UTF-8 makes `subprocess.run(..., text=True)` raise `UnicodeDecodeError`, which `build_index` does not catch (it catches OSError and SubprocessError). `main` catches it as ValueError and exits 3 with "settings.local.json exists but is not a JSON object" (reproduced with `fake/colgrep` printing bytes `\377\376`; the lab folders were already written). The `text=True` is from 9e4bbac, before this claim, but the claim's docstring "never raises" and the new parsing of this output sit on it. APFS paths are UTF-8, so a real trigger is unlikely.
3. ANSI colour and emoji prefixes are not parsed (the regex is anchored at line start): `\x1b[32mIndexed ...` and `📂 Indexed ...` fall to the fallback, which prints colgrep's own words. Harmless (`--color never` is passed, the real lines have no prefix) and the claim says so.
4. The briefs.md sentence says "one run in seven, told 'no claim file is needed', ran its script inline". The source (S-w03-author-w03-2-4) is one run told that sentence (it skipped the file) against six runs not told it (all wrote a file). The sentence reads as 1 of 7 runs told, a base rate of about 14%; the observed split is 1 of 1 with the sentence and 0 of 6 without. It also states as fact what the claim head labels CONJECTURE (cause), and the sentence is about 40 words with a parenthesis.
