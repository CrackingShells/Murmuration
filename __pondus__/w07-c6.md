# w07-c6: The permission guard as one Rust binary, `murmuration guard`, started in exec form from `${CLAUDE_PLUGIN_DATA}`, gave the Python guard's decision on all 20,847 gated events (0 differences), blocked the Bash call when the binary crashed, hung, was missing or could not be run, fell back to the Python guard where no binary fits, and cost 16 ms less CPU and 16 ms less start-to-exit time per call outside the platform (600 pairs) and 23.5 ms less recorded hook time inside it (19 of 19 pairs)

label: MEASURED
scope: The 32 guard rows of `hooks/hooks.json` on macOS (aarch64 and x86_64 binaries built; only aarch64 run), Claude Code 2.1.304, haiku headless sessions in default permission mode with an allow list, Python 3.12.12 (miniforge) as the reference; A is the guard rows in exec form (`python3 -S -I permission_guard.py`), not today's string form. Equality is on exit code, stdout and the optional log line for string-valued events. It does not cover Linux or Windows (no target built), the Desktop app, auto mode's wall time (the hook hides behind the classifier there; only CPU is shown), a git-installed plugin's real data folder (the sessions used `--plugin-dir`, data folder `~/.claude/plugins/data/<name>-inline`), `budget.py` and `handback.py`, nor JSON events whose tool-input fields are floats, lists or objects where a string is expected (10 of 189 such events differ, reported apart).

method: experiment. Branch `w07-p5-rustguard` (from ac07ab3), worktree `/private/tmp/murmuration-w07/author-w07-5/wt`. Tool fit: Rust for B (the protocol's binary), Python for the replay and session drivers (JSON, subprocess), C for the spawn bench (explorer-w07-a's driver extended with stdin from a file).

**What B is.** A std-only crate `rust/` (no dependencies, `Cargo.lock` lists one package; `#![forbid(unsafe_code)]`, `cargo clippy --offline` clean) with one binary `murmuration` and one subcommand `guard`; `budget` and `handback` would be further subcommands (not built). `guard` is a port of `scripts/permission_guard.py`, over code points because a Python `str` read from JSON can hold a lone surrogate; the regular expressions are written out by hand, the Unicode classes (`\s`, `\w`, `\d`) come from range tables that `rust/gen_tables.py` generates from Python 3.12.12's own `str.isspace/isalnum/isdecimal`, the JSON reader copies `json.loads` (NaN, duplicate keys, lone surrogates, 4,300-digit ints, depth 9,998), the failure names are Python's (`JSONDecodeError`, `AttributeError`, `TypeError`...). A panic in the decision becomes a deny. Binaries for the two darwin targets are committed under `bin/<target>/`; no other target built; no download. `scripts/install_binary.py` (SessionStart, exec form) copies `bin/<target>/murmuration` to `${CLAUDE_PLUGIN_DATA}/bin/murmuration` when absent or different (sha256, atomic), writes a `#!/bin/sh` launcher for `permission_guard.py` when no binary fits, and on any error exits 1 with a message on stderr. The 32 guard rows are `"command": "${CLAUDE_PLUGIN_DATA}/bin/murmuration", "args": ["guard"], "timeout": 20, "onFailure": "block"`. `scripts/check_guard_equal.py` is the replay; `scripts/git-hooks/pre-commit` and `.github/workflows/guard-binaries.yml` are files for the maintainer, not installed or pushed.

The 10 typeconf differences are all Rust deny (`UnsupportedType`) against Python allow or a different exception name, for a float, list or dict where a string is expected (`content`, `new_string`, `new_source`) and a non-empty list as `command`; 189 − 10 events of odd JSON (NaN, duplicate keys, a BOM, lone surrogates, 4,300 and 4,301-digit ints, depth 9,997 and 9,998 and 9,999, invalid UTF-8 on stdin, non-dict `tool_input`, non-string `cwd`) agree, including the exception names. The one stress difference is the Python guard timing out (over 40 s) on a 300 kB word where Rust answers in 0.05 s (S-w07-author-w07-5-1). What was not tried: a mutation test of the checker (S-w07-author-w07-5-5); `~name` expansion (the port has no user database).

**g2 (failure) — passes; MEASURED live, with one limit.** Live (`g2_live.md`): crash (a Mach-O stub exiting 101): Bash blocked, the model saw `failed; blocking because onFailure is "block"` and the stub's stderr; hang (stub sleeps 60 s): blocked after the 20 s timeout, `timed out; blocking because onFailure is "block"`; binary missing from the data folder (the folder read-only): the SessionStart copy failed visibly (hook error with the PermissionError text) and the Bash call was blocked (ENOENT); an unrunnable file (ENOEXEC, an accidental empty stub): blocked 4 of 4. With `bin/` absent the installer wrote the launcher, and live six commands were decided by the Python guard through it (3 denied G1, G3, G2; 3 ran). Offline, the launcher over 121 registered + 4 malformed + 1,500 + 300 fuzz + 189 typeconf events: 0 differences from A (`g2_launcher_equal.txt`); the installer's 10 cases (fresh copy, no-op second run, replaced when different, absent, unwritable folder, folder under a file, either variable unset, launcher) all behave as stated (`g2_offline.txt`). Limit: the data folder is the `--plugin-dir` one; a marketplace install's folder was not tried.

**g5 (what it costs to ship) — reported.** Size 419,184 B (aarch64) and 407,600 B (x86_64) with `opt-level = "s"`, LTO, strip. Dependencies: none (the crate is std only). Build: clean release build 2.7 s per target (`--offline`). Source: 1,900 lines of Rust in five files plus 152 lines of generated tables, against the Python guard's 416 lines. One such first exec per data folder per machine, so once per install and per plugin version.

## What is shown, in the three units
- CPU: 16.0 ms less per guard start (g3, 600 of 600 pairs): shown for every Bash call and every matched Write/Edit call, in either permission mode.
- Start (spawn to exit of the guard process, outside the platform): 15.9 ms less (g3), reaching the one-exec floor.
- Wall, in the platform: the guard's recorded hook duration is 23.5 ms lower (g4, default mode). In auto mode the PreToolUse hook runs beside the classifier (explorer-w07-g: 642 against 631 ms to dispatch), so the call's wall saving there is about zero and only the CPU saving stands; on the Write/Edit rows and in default mode the wall saving is what g4 shows. A's rows are in exec form (P3's form); against today's string form the saving is larger (S-w07-author-w07-5-6).

## What this closes
It closes the question whether the permission guard can be one Rust binary, selected per platform at session start with no shell and a Python fallback, that keeps the Python guard's decisions on all string-valued events and its fail-closed behaviour, and what that costs to ship and saves per start on this machine. Outside that scope: a Linux or Windows binary, a marketplace-installed plugin's data folder, auto-mode wall time, and whether `budget` and `handback` can follow (they would carry their own tests).
