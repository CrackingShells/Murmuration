## What is missing (said now)

- **The sync side of the crash trace.** The identical-command rows were merged, so no sync crash ran, and the 12 sessions were used. Main's script never crashes visibly (it catches everything), so "on main" has no trace to compare against; a sync crashing hook was the only control. Not measured.
- **A main arm for r3** beyond one session; the time to first API request is dominated by the user-level sync hook (about 0.2 s), so a 10-session main arm would very probably show the same median, but that is an inference.
- **Cancellation at the end of a `-p` session** was not stressed: the async hook took 0.2 to 0.7 s and the sessions lasted 7 s or more. explorer-w07-c measured a long async hook being cancelled at teardown. A prompt submitted as the last act of a `-p` session (an immediate exit) would be at risk; not run.
- **Desktop:** whether the record is on disk soon after the hook starts in a Desktop session, and whether Desktop honours `async` on this hook, are not measured; the first typed prompt and the first spawned-session message after the merge are the check.
- The entrypoint behaviour is as v0 found it: a `claude -p` started from a Desktop session's Bash inherits `claude-desktop` and is dropped like a spawned session; only the terminal-like sessions (11 `CLAUDE_*` variables removed) were kept.
