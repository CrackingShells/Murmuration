method: Experiment, same protocol P4 (metrics (a)-(e)). What changed since w08-c10 (commit 274e09e): (1) `_spans`/`spans` replace the per-opener `_close` scan: one pass over a text with a stack of open quotes, backticks and parentheses finds every matched substitution, so the cost is linear in the text (the old scan went to the end of the text for every unmatched `$(`); inside a `$( )` the body of a heredoc (`<<WORD`, `<<'WORD'`, `<<-WORD`) is skipped as data when looking for the closing `)`, so a body with `(x`, `1) one`, `it's` no longer hides it (finding 1). Outside a substitution the body is still read as commands, as before, because a heredoc fed to `bash` or `python` is code; nothing read before is dropped. (2) A quote still open at the end makes the pass run again with quotes as ordinary characters, as the plain splitter does (found while writing this: `echo it's; claude -p "$(cat f)" --bare` was allowed on w08-c10). (3) G1's test "the command names claude" also looks at the strings expanded from `env -S` and `sh -c`, where `-Sclaude` glues the word to the option (finding 2). (4) The cap: work is the number of characters scanned, a text scanned once costs its length and each nesting level scans its inside again; above 10,000,000 the command is denied `G?` (finding 3). Boundary of the cap: nesting depth about 3,200 (a command of about 10 KB written as `$(` x k ... `)` x k, 2.7 s in Python, 0.09 s in Rust), or a long text of depth d with length x d above 10 million; the 200 KB heredoc prose with 800 bare `$(` costs 0.2 MB scanned (one pass, depth 1). No ordinary worker command has a nesting depth above 5.
