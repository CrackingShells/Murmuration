## What failed, and why it matters

1. **The record is not on disk while the hooks run.** In 10 of 10 first prompts with the branch script as a hook, the transcript file did not exist at hook start and the prompt's record became readable 0.30 to 0.38 s after the hook started, that is just after the script's own 0.3 s poll ended and the hook exited. With only a probe hook that returned at once (p00), the record was readable 0.088 s after hook start; for the later prompt of that session 0.045 s (the same for a resumed session with both hooks, 0.339 s, and with the probe only, 0.045 s). A first test run, not saved, had the probe poll for 2 s inside the hook: the file appeared 2.0 s after hook start, again when the hook exited. The reading that fits all of it: the platform persists the prompt record after the UserPromptSubmit hooks have finished, so a hook that polls for its own prompt's record can only time out. [MEASURED: q2_live.txt, q2_probe.jsonl; the mechanism is an inference from those numbers, CONJECTURE, not read from code.]
2. Consequence for the branch as built: in headless sessions the lookup returns "unknown", the text rule decides as before (so the sdk prompts of headless runs are stored, as on main), and each prompt waits 0.3 s for nothing (q3b, miss case). That is a 300 ms regression on every prompt, which the registered q3 bound (30 ms) forbids. Whether Desktop behaves the same is not measured: explorer-w07-f found the record's timestamp 0.2 s and 0.9 s before the hook ended (n = 2), but the timestamp is the in-memory creation time, and here the timestamp also preceded the hook start while the file did not yet exist.
3. A design that the data point to, not built and not tested end to end: let the hook return at once and have a detached child wait for the record (the probe's child found it in 0.045 to 0.088 s, n = 2, with a fast hook; it ran to completion after the hook exited), then append by the origin rule, falling back to the text rule at a timeout. CONJECTURE: two sessions only, and an appender that outlives its hook has not been tried in Desktop.

## Which fields tell a Desktop `sdk` prompt from an `sdk-cli` one

- In the transcript record, one field: `entrypoint` (`claude-desktop` against `sdk-cli`). Every other field of the record is the same for the two (`promptSource: sdk`, `turnOrigin: sdk`, no `origin` object, `userType`, same key set: q2_probe.jsonl, rows f00 and t00; fields_by_origin.txt). MEASURED, n = 1 for sdk-cli live, 2 in the lab's transcripts (one of them that live session).
- But `entrypoint` is the environment variable `CLAUDE_CODE_ENTRYPOINT` of the process that started the session. A `claude -p` started from a Desktop session's Bash tool inherits `claude-desktop`; of the sdk-origin records without an origin object in the lab's transcripts (1882 at the last count), 1880 say `claude-desktop` and 2 say `sdk-cli` (the user's own terminal run, and my terminal-like session). So the field separates "started from a terminal" from "started under the Desktop", and it labels the lab's own headless probes (and the agents' workers) as Desktop sdk, which the rule drops. A person's `claude -p` typed in the Desktop's terminal tool would inherit it too and be dropped.
- In the hook payload: no field of the 8 keys (`session_id, transcript_path, cwd, permission_mode, prompt, prompt_id, hook_event_name, scratchpad_dir`) names the entrypoint. `scratchpad_dir` was present in the 13 sessions started with the Desktop's environment and absent in the one terminal-like session (n = 1, CONJECTURE that it separates them). The hook's own environment holds `CLAUDE_CODE_ENTRYPOINT` with the same value as the record (claude-desktop in 13 sessions, sdk-cli in the terminal-like one), so a hook can read it without the transcript. It cannot, by itself, separate a typed Desktop prompt from a spawned session's first message: both run under `claude-desktop`; only `origin.kind` (human or absent) does, and that needs the record.
- The terminal-like session was made by removing 11 `CLAUDE_*` variables from the environment of `claude -p` (list in `w07c2_q2_run.py`); a real terminal was not used.
