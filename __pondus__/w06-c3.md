## What would be different if the claim were false

A field the scripts read would arrive empty or wrong (m1: compared field by field with the platform's own stdin, recorded by a `command` hook beside the server); a hook would not fire on some event or thread (m2: server log against the transcript); the server's tool would show in a worker's or the lead's request (m3: the control arm with the tool allowed does show it, +64 tokens per worker, so the check can fail); a stopped server would drop the deny and the block without any record (m4); the median would exceed 10 ms (m5); or an injected line, a deny or a block would not reach the model (m6: each carries a random nonce the model must quote or the transcript must hold).

**Rule (protocol): stage 2 runs only if m1, m2, m3, m5 and m6 pass and m4 shows a visible failure within 10 s.** m1, m2, m3, m5, m6 pass. m4 shows a visible failure within 10 s in the registered scenario and in (b); it fails the 10 s clause in the hang variant (c). By the letter the gate is met; by the strict reading of "the turn waits no more than 10 s" it is not, for a hung server only. Two facts stand beside the pass for the PI: the effect of an outage (deny and block silently lost) is recorded in the transcript only, and the platform's restart of a killed server (a) means a single kill is not an outage. The first is a design input for stage 2's s3 (announce the outage), not an artefact of this test.

What this closes: the claim that an `mcp_tool` resident server cannot carry the payload fields, firing, effects or latency of Murmuration's budget and hand-back hooks in this platform version. One thing outside that scope: the server did not run the budget or hand-back logic, so its own CPU, its state under two concurrent workers and any difference in output from main are untested (stage 2's s1 to s4).

## method

Why the tools fit: Python standard library for the server (the brief), `claude -p` headless for the platform behaviour (the only place the hooks run), `python3 -I` scripts for deriving tables from the transcripts and the debug files (exact counting).

Design. `w06c3_build_plugin.py` builds the plugin in three variants (`live`: server and mcp_tool hooks; `truth`: the same plus a `command` hook on each registration that appends the platform's stdin to a file; `off`: agents only; `--open`: control with the tool allowed). Registrations as the protocol lists: SubagentStart; PreToolUse `Agent|Task`; PostToolUse; PostToolBatch; SubagentStop; PreToolUse and PostToolUse `SubagentHandback`, each `mcp_tool` on server `plugin:wt:res`, tool `hook`, with `timeout: 10` as in `hooks/hooks.json`. The worker agent has `tools: Bash, Read, Write` (no server); the lead is the main thread (`--agent wt:lead`) with `disallowedTools: mcp__plugin_wt_res__hook`. Models: parent haiku (`--model haiku`), worker haiku (agent file). `w06c3_resident_server.py` answers by event: SubagentStart: an `additionalContext` with a random nonce; PreToolUse `Agent` with `DENYME` in the prompt: `permissionDecision: deny` with a nonce; PostToolUse with `BLOCKME` in `tool_input.command` (a test-only extra field): `decision: block` with a nonce; otherwise empty text; mode `quiet` answers nothing always (the m3 arms). A `refuse` file ("exit" or "hang") makes a restarted server exit or hang: a test device for m4 (b) and (c) only. `w06c3_run.py` runs one scenario with `CLAUDE_CODE_SHELL=/bin/bash`, `--plugin-dir`, no `--max-budget-usd`, cwd `/private/tmp/murmuration-w06/author-w06-3/work`; everything under `/private/tmp/murmuration-w06/author-w06-3/`. `w06c3_analyze.py` derives m1 to m6 from `server.jsonl`, `truth.jsonl`, the session transcripts and `dbg.log`; `w06c3_tables.sh` writes `tables.md`.

Runs (22 runs in `runs/`, in the order of `w06c3_run_all.py`): `t_auto0-1` (scenario `full2`, auto), `t_byp0-1` (`full`, bypassPermissions), `v0-4` (`lean5`, auto, 25 workers), `m3_off0-2`, `m3_on_0-2`, `m3_open` (`lean2`), `m4a0-1`, `m4b0-1`, `m4c0-1` (`outage`). Pilots (`out_pilot*`, 4 runs, a plugin build before `timeout: 10` and the `refuse` device in two of them) shaped the design and are excluded. Counts: 22 full runs, 4 pilots, 9 quick runs. Seeds: none exist for the model; the scenarios and the order of the pair arms are fixed in `w06c3_run_all.py`. Model nondeterminism is why every metric has n above 1.

Commands. Full (22 headless runs, about 15 minutes, about USD 0.29 as `claude` reports `total_cost_usd`, summed; the pilots USD 0.05): `python3 __instrumenta__/w06c3_run_all.py` then `sh __instrumenta__/w06c3_tables.sh > tables.md`. Quick (9 runs, about 6 minutes, runs under `runs_quick/`): `python3 __instrumenta__/w06c3_run_all.py --quick` then `sh __instrumenta__/w06c3_tables.sh /private/tmp/murmuration-w06/author-w06-3/runs_quick`. Raw run directories carry account identifiers and are not committed. The quick command was run once (9 runs, all finished): m1 all fields equal on 47 of 47 calls (truth runs), m2 87 of 87 rows equal, m3 worker request 0 OFF 5945 and ON 5938 (the full run's pairs went the other way; same shape hashes) and control 6004, m4 (a) restart and no failure, (b) 25 error records and the deny lost, (c) waits 10.0, 10.0 and 7.6 s, m5 all 64 calls median 1 ms (max 7; SubagentStart debug-log median 6 ms, n 5). Its table is `/private/tmp/murmuration-w06/author-w06-3/quick_tables.md` (not committed; reproduced by the command above).

Interpretations I took where the protocol is silent, for the verifier to challenge: (1) m3's "0 tokens" read as in the table; (2) m4's "stopped by its own pid" is variant (a), (b) and (c) are additions; (3) m5's `SubagentStart` has no `durationMs`, so the debug-log measure stands; (4) m2's SubagentStop reference is the platform's hook record; (5) a PostToolUse command hook and the server's PostToolUse call for the same tool are separate rows; the platform runs one command hook for two registrations with the same command text (the truth log has one record where the server has two), which does not matter for the server (different inputs).
