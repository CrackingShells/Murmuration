## What would be different if the claim were false

The claim has two halves, and each half has its own way to fail.
- Same outputs: an import moved out of the quiet path that a note, a block, a deny or a hand-back needs, a JSON reader or writer that differs from `json` on one real value, a lost `-I` side effect, or a changed command string would change an answer, a log line, a hand-back file, a state file or an exit code. Shown that the checks can fail: three mutants of the build give DIFF on 197, 11 and 55 of 197 transcripts (cost, ceiling, reader), a mutant row of `hooks.json` gives DIFF in the command-mode replay, and a mutant of `dumps` fails the selftest.
- At least 25 ms: the median platform-recorded start of a worker's budget.py PostToolUse would be 25 ms or more below main's in every pair. It is 18 to 42 ms in eight pairs and -30 ms in one, and 3 of 9 pairs reach 25.

## Why 25 ms cannot be reached by a lean Python start here (MEASURED, quiet machine, load 2 to 2.5)

`hook_cost_time.py` paired, `sh -c 'cd LAB && <command from hooks.json>'` by `posix_spawn`, payload on a socket, a worker on the 0.31 MB transcript, n = 40 pairs: main 81.2 ms, build 61.2 ms (wall median), CPU 39.6 and 19.3 ms; p90 82.8 and 62.7. Floors in the same machine state (`cmd_cost_interleaved.py`, n = 40): `sh :` 30.0 ms, `python3 -S -I -c pass` 55.1 ms (CPU 13.2), the same importing `os`, `sys`, `_json`, `fcntl` 56.8 ms (CPU 15.1), plain `python3 -c pass` 69.5 ms (CPU 28.3). So a worker start is 4.4 ms above the least a Python hook that reads JSON and takes a lock can cost, and **main's own start is only 26.1 ms above the bare `python3 -S -I` floor**: the threshold of 25 ms leaves 1.1 ms for everything the script does. On the platform's record the same gap shows as 22 ms per pair (pooled 26 ms) because the platform adds its own spawn cost to both arms.

## What the build buys (ESTIMATE, formula and inputs stated; not an achieved result)

- Per start, worker, quiet machine: 20 ms wall (25%), 20 ms CPU (51%); 5.5 MB transcript: 107.5 to 90.3 ms (17 ms, the transcript is still read from its start, which is 35 ms of the long-worker start [source: `__pondus__/w04-c5.md`, ablation table]); main thread: 80.4 to 55.8 ms (25 ms, n = 15) in the bench, without a shell gate.
- Per wave: 1580 worker starts of 1788 in a wave like wave 4 [source: `__reports__/wave-06/explorer-w06-b/00-findings_v0.md`, table row 1 to 4] times 20 ms = about 32 s of the 161 s of serial hook time, and times 20 ms of CPU = 32 s of CPU. ESTIMATE: starts per wave times the bench difference; it takes no account of starts overlapping in the platform.
- What it costs: one more file in `scripts/` (`run_hook.py`, 11 lines), +94 production lines, a JSON reader and writer on private `_json` entry points (with a fallback to `json`), and bytecode written to `scripts/__pycache__` in the plugin folder because `-I` ignores `PYTHONDONTWRITEBYTECODE` (git-ignored by `.gitignore` line 8; where the folder is read-only the code is compiled at each start, as before). Not built, and the reason the number is not higher: the incremental transcript read of w04-c5 (about 100 more production lines, so e4 would fail), and a shell gate for main-thread starts (about 24 ms more for 11% of starts).

## What this closes, and what it does not

Closes: whether a lean start of the two hooks (lazy imports, no `site`, no environment, cached bytecode, a C JSON scanner) can keep every recorded output and cut a worker's PostToolUse start by 25 ms on this machine under E2's rule: it keeps the outputs (e1, e3, e4) and cuts 20 to 22 ms, so no. Outside that scope: whether E2's threshold is the right one (26 ms is the most a Python start can save here, so the PI may judge 20 ms and 20 ms of CPU a start enough to land at the user's "reclaim it even if small" reading, a decision this claim does not take), and whether the saving is 22 ms or 26 ms on the platform (the per-pair median and the pooled median disagree by 4 ms at this noise).

## method

Why the tools fit: Python standard library for the replay, the timing and the derivations (exact counting over 197 transcripts, process starts by `posix_spawn`), headless `claude -p` for the platform's own record (the only place a hook's platform-recorded duration exists), POSIX sh for the drivers.

Setup (scratch `S=/private/tmp/murmuration-w06/author-w06-6`; the scripts have this path built in): `mkdir -p $S/old $S/new056 && git archive dbd32e7 | tar -x -C $S/old && git archive 056312d | tar -x -C $S/new056`. Nothing below the repository; `CLAUDE_CODE_SHELL=/bin/bash`; haiku; no `--max-budget-usd`; `--permission-mode auto`; the export of the commit passed with `--plugin-dir` (the runner creates `$S/export_<commit>` and sets the agents' `model:` lines to haiku in both arms).

The build (056312d): `handback.py` gains `loads` (the C scanner of `_json`, no `json` import), `dumps` (equal to `json.dumps` for what `loads` yields), `Lazy` (a regex compiled at first use), and imports `re`, `datetime`, `hashlib` only in the paths that need them; its name check is done without `re`. `budget.py` takes `loads` and `dumps` from it, imports `glob`, `datetime` and `re` where used (a model named as a price row needs no `re`), and reads stdin as bytes. `scripts/run_hook.py` inserts its own folder in `sys.path` and imports and runs `main()` of `budget` or `handback`, so Python keeps their bytecode. The 8 command strings of `hooks.json` are `python3 -S -I "${CLAUDE_PLUGIN_ROOT}/scripts/run_hook.py" budget` or `handback`. Variants tried before the choice (`w06c9_variants.py`, bench n = 6 and n = 15, loaded machine): `-S -I script` (67.6 ms on worker-short), `-S script` (71.7), `-S -I -c 'import budget; budget.main()'` and `run_hook.py` (61.0 and 60.9), main 81.1: bytecode caching is 6 ms of the saving, `-I` 4 ms.

Full commands (about 12 minutes of the machine and USD 0.30 for the 20 headless runs; no seeds exist for the model, and the replay and the bench are deterministic apart from the clock):
- e1 replay: `OLD=$S/old NEW=$S/new056 OUT=$S/e1full sh __instrumenta__/w06c9_e1.sh` (about 4 minutes: sequential, parallel and three mutants side by side; results in `$OUT/results/e1_*.txt`, copies in `__reports__/wave-06/author-w06-6/e1_*.txt`). Quick (4 seconds): the same with `QUICK=1` (the first 5 transcripts).
- e1 process mode: `python3 -I __instrumenta__/w06c9_e2e_commands.py --old $S/old --new $S/new056 --out $S/cmd_ok` and with `--mutate`.
- e2: `MAIN_COMMIT=dbd32e7 NEW_COMMIT=056312d PAIRS=5 TAG=e2a sh __instrumenta__/w06c9_e2.sh` and `PAIRS=4 TAG=e2b` (the runner takes the export of each commit, runs the two arms of a pair at the same time, and `w06c9_measure.py` prints the tables). Quick (about 1 minute, USD 0.03): `PAIRS=1 TAG=q`.
- bench and floors: `TAG=t3 N=40 NOFLOORS="" ONLY="--only post_tool_use:worker-short" VARIANTS="--variant old=$S/old --variant new=$S/new056" sh __instrumenta__/w06c9_timing.sh` (needs the two worker transcripts of w04-c5 under `~/.claude/projects`, and `$S/reports_src` = a copy of main's `__reports__` without the dangling `work_link`), and `python3 -I __instrumenta__/cmd_cost_interleaved.py <cases of sh :, python3 -S -I -c pass, ...> --n 40`.
- e3 and e4: `python3 -I __instrumenta__/w06c9_shape.py $S/old $S/new056`, `python3 -I __instrumenta__/w06c9_lines.py $S/old $S/new056`, `sh __instrumenta__/w06c9_selftests.sh $S/new056`; all tables of the claim: `OLD=$S/old NEW=$S/new056 OUT=$S/tbl RES=<folder> PAIRS="e2a_1_main:e2a_1_new ..." sh __instrumenta__/w06c9_tables.sh`.
- Edited shared helper: `__instrumenta__/hook_cost_time.py` now reads the script name from a `run_hook.py <name>` command (one line).

Interpretations for the verifier to challenge: (1) "platform-recorded `durationMs`" is the debug file's `finished with status (N ms)`, because a command hook that prints nothing leaves no transcript attachment (as in w06-c4); (2) a start is a worker's when it finished between a worker's `start` and `end` log lines and is not an Agent-tool event; (3) e2 is read per pair, as registered ("in every pair"), and the pooled 26 ms is reported, not used; (4) the 4 extra pairs (e2b) were run after seeing the first 5, to test the result at lower load, and are reported in full with the first 5 (all 9 together decide nothing differently: the rule fails on either set); (5) e4's "production lines" is wc -l outside the selftest block, docstrings and blanks included; with whole files it is +154, which would fail a limit of +100 if the limit meant whole files; (6) the replay clock is the event's, so the real clock's effect on `active_s` is covered only by the process-mode run, which drops `t` and `active_s` from the comparison.
