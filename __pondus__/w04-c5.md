### The lean version (66a0902)

1. `hooks/hooks.json`: PostToolUse and PostToolBatch of `budget.py` start through `p=; while IFS= read -r l || [ -n "$l" ]; do p=$p$l; done; case $p in *'"agent_id"'*) printf '%s\n' "$p" | python3 -S -I "${CLAUDE_PLUGIN_ROOT}/scripts/budget.py";; esac`: the main thread's event never starts Python; every other registration starts `python3 -S -I` (no `site`, no environment).
2. `budget.py` and `handback.py` are 80-line entries over `budget_core.py` and `handback_core.py` (Python keeps their bytecode in `scripts/__pycache__`, git-ignored; `-I` ignores PYTHONDONTWRITEBYTECODE; where the folder cannot be written the code is compiled at each call, as before). The selftests moved to `*_selftest.py`.
3. The hot path imports only `os`, `sys`, `time`, `zlib`, `fcntl`; JSON is read with the C scanner of `_json` and written by a 40-line writer (`handback_core.loads` / `dumps`, equal to `json` on what `json.loads` yields, 400 random objects in the selftest, `json` as fallback); `re`, `datetime`, `hashlib`, `json` load only on the paths that need them (a note, a raise, a hand-back, a log line).
4. The transcript is read from the byte offset where the last check stopped (`sc` in the state file, 10 KB for 148 requests; the last 48 bytes before the offset as a guard; the cost of each finished request; the last 3 requests in full). A shrunk file, a failed guard, or a record that names a finished request again triggers a read from the start. The unfinished last line waits for its newline (the old code would have failed to parse it and answered nothing).
5. A resume's SubagentStart no longer reads the transcript (the old code read and dropped it); the agent's name is looked up when a line is written, not at every call.
6. `handback.py` report check: the deny marker is tested first (a second hand-back is never searched for), then the convention's own folder, and all of `__reports__/` is walked only when both fail.
7. `lab_status.py`: `subprocess`, `tempfile`, `contextlib`, `io` are no longer imported at the top, and its selftest sits in `lab_status_selftest.py`: a session resumed through `resume_brief.py` (which imports it) takes 40.3 instead of 50.5 ms of CPU (measured, n = 30); `lab_status.py` itself still takes 0.9 s wall (0.55 s CPU) per call to read the lab's transcripts (not changed).

## Decision (E4, as pre-registered)

- Selftests of every changed script pass: yes (budget, handback, lab_status; resume_brief and user_words, which import or sit beside them, also pass).
- Notes, logs and hand-back copies identical on replayed payloads: yes, 291 of 291.
- Main-thread starts, median wall time down by at least 50%: yes (PostToolUse -65%, PostToolBatch -63%; CPU -91%).
- Long-transcript worker starts, median wall time down by at least 50%: not unambiguously. Per registration it is -53% for PostToolUse and -47% for PostToolBatch; pooled over the two that run at every tool call -51% (interval -47% to -53%, so it contains the threshold); SubagentStop -43%. By CPU time it is -78% in every run.
- No dependency outside the standard library and POSIX sh: yes (`_json` and `zlib` are standard-library C modules; `json` is the fallback where `_json` is missing).

Read literally ("worker invocations on the long transcript: median wall time down by at least 50%", every registration), the second criterion fails for PostToolBatch, and E4's rule then says: report the measurements and propose nothing. Read as the cost of the two starts every tool call pays, it holds at the edge (0.49). The wall figure is dominated by what the platform spends on a start, which no script change touches, and by a load average of 5 to 13 on this machine; I therefore do not claim the lean version crosses the threshold. The PI decides which reading governs; the version is built, at 66a0902, and is in the working tree as filed.

What the PI may weigh beyond the rule: the lean version removes 91% of the main thread's hook CPU and 78% of a long worker's; the cost is 5 more files in `scripts/` (two modules, three selftests; `scripts/` held 6 scripts), a 40-line JSON writer and a 20-line reader that exist to avoid a 6 ms import, a state file that grows with the number of requests (10 KB at 148), bytecode written in the plugin folder, and a hook command in `hooks.json` that is no longer one line of Python.

## Notes for the scripts I do not own

- `user_words.py` (one start per user prompt and per queued task notification; 24.5 ms CPU): `python3 -S -I` alone brings it to 16.7 ms (measured, n = 30, with the version at 41c75ea). Its stdin is read as text (`sys.stdin.read()`); under `-I` the locale decides the decoding (UTF-8 mode is on for the C locale; with an ISO-8859 locale a non-ASCII prompt would be misread); reading bytes, as `budget.py` does, removes the question. Its `datetime` and `re` imports could load on the path that writes.
- `resume_brief.py` (SessionStart resume or compact; 50.5 ms CPU at 41c75ea): 40.3 ms with the lean `lab_status.py`, 29.9 ms with `-S -I` besides.
- Neither is changed here; `hooks/hooks.json` still starts them as `python3 <script>`.

## What this closes, and what it does not

Closes: whether a lean rewrite of the budget and hand-back hooks can keep every recorded output while cutting what each start costs, on this machine: it can, to the floor of starting a shell for the main thread, and to 5 ms above the floor of shell plus interpreter for a worker. Outside that scope: the platform's own cost of spawning and waiting for a hook, which is paid before our command runs and was not measured; and whether the PostToolUse ceiling check (which acts only from 1.5 of the budget, once per worker if ever) could move to the batch check so that a tool call pays one start instead of two. That last change alters what the hook sends (the block would follow the spend of the previous request, not the present one), so it is a separate claim with its own test, not made here.
