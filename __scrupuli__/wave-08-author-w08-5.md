## symbols
- `pool`: in a dispatch record, the names (sorted, comma-joined) of the records of one agent type that were fresh when the first of their starts took its record; it marks every later claimant of the pool as unable to tell which name is its own.
- `name_unconfirmed`, `name_candidates`: fields of a `start` line in `__statera__/harness.jsonl` whose agent took a record from a pool; the line's `name` is then the id-based name (`murmuration-<role>-<id8>`), not a guess.
- `named`: a harness line (agent_id, name, type) written when the Agent tool's answer names an agent whose `start` line already exists.
- answer: the PostToolUse event of an Agent call; `tool_response.agentId` is the agent's id.

## S-w08-author-w08-5-4
`PostToolUse` on the Agent tool arrives before the agent's start only for background dispatches, and then only by 70 to 90 ms in the headless sessions (r3, py_bg, rs_bg: pattern A then S per dispatch, but one `named` line per session shows the last agent's answer came after its start). The fix therefore ties starts to dispatches by id in most background cases and falls back to "unconfirmed" in the rest, plus a `named` line afterwards; it is not a guarantee. If the platform ever delivered answers after starts for every dispatch, every start of a batch would be marked unconfirmed and only the `named` lines would be right. I do not know whether a hook can ask the platform for the agent id of a pending dispatch earlier (a field in PreToolUse, which carries `tool_use_id` but no agent id), and could not find one in the 8 keys of PreToolUse or the 8 of SubagentStart.
